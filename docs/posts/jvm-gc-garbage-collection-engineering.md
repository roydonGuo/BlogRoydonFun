# JVM 垃圾回收工程实践：可达性分析、三色标记、分代收集与收集器选型

<img src="/images/posts/jvm-gc-garbage-collection-engineering-knowledge-map.webp" alt="JVM 垃圾回收工程实践：可达性分析、三色标记、分代收集与收集器选型知识串联图" style="border-radius: 10px;" />

GC 管的不是整个 JVM，而是堆里"能不能被根引用链摸到"的对象。本文从判定对象死活的两条路（引用计数 / 可达性分析 / 三色标记）讲起，串起四种引用、三种回收算法、分代模型，再到 Serial / Parallel / CMS / G1 / ZGC 的取舍，并给出 Spring Boot 调优、GC 日志、OOM 排查与选型建议。

## 先说结论：GC 只解决"堆里哪些对象该回收"

很多人把 GC 想成"自动管内存的魔法"，但落到工程上真正要回答的只有三个问题：

1. **哪些对象算"死"了？** —— 不被 GC Roots 引用链触及的对象，即判定为可回收。
2. **怎么回收才高效？** —— 标记-清除 / 复制 / 标记-整理三选一，本质是在"碎片、内存占用、停顿"之间做权衡。
3. **谁来回收、何时停顿？** —— 不同收集器在"吞吐优先"和"停顿优先"之间取舍；JDK 9 起 **G1 是默认收集器**，JDK 15 起 ZGC / Shenandoah 已可用于生产但仍非默认。

先记住四条工程结论：

- **GC Roots 是判活的唯一入口**：虚拟机栈局部变量、静态变量、常量、JNI 引用等能直接摸到的对象是"根"，顺着根往下爬，爬不到的就是垃圾。
- **引用计数法在 JVM 不用**：互相引用会成环导致永远不回收，HotSpot 用的是可达性分析 + 三色标记。
- **分代收集是事实标准**：新对象大多"朝生夕死"，所以堆被切成新生代（Eden + 2 个 Survivor）和老年代，用不同策略分别处理。
- **STW（Stop The World）不可避免，但可以被压缩**：标记起点、重新标记等阶段必须暂停用户线程，现代收集器把最耗时的遍历做成与应用并发。

> 版本基线：本文以 **HotSpot / OpenJDK** 为基线，默认 GC 行为按 **JDK 9–21** 说明，涉及 JDK 8 差异与 ZGC / Shenandoah 状态均已标注。事实核对日期：**2026-08-19**。主要参考：[JEP 248 Make G1 the Default GC](https://openjdk.org/jeps/248)、[JEP 377 ZGC Production](https://openjdk.org/jeps/377)、[JEP 379 Shenandoah Production](https://openjdk.org/jeps/379)、[JEP 439 Generational ZGC](https://openjdk.org/jeps/439)。

## 一、判定对象死活：两条路，JVM 走第二条

### 1.1 引用计数法（不用）

给每个对象挂一个计数器，被引用 +1、取消引用 -1，归零即可回收。

- 优点：判定快、回收及时，不需要全局扫描。
- 致命缺点：**循环引用**。A 引用 B、B 引用 A，彼此计数器都不为 0，但外部已没有任何人能摸到它们，永远不会被回收。

Python、Objective-C 用引用计数（配合逃逸分析/弱引用解决环），但 **JVM 不采用**。

### 1.2 可达性分析（JVM 采用）

从一组 **GC Roots** 出发，沿着引用关系向下搜索，凡是能连上的对象标记为"存活"，搜不到的就是要回收的垃圾。

可作为 GC Roots 的对象：

| 来源 | 说明 |
|---|---|
| 虚拟机栈（栈帧局部变量表）中引用的对象 | 正在执行的方法里 `new` 出来的局部变量 |
| 本地方法栈中 JNI（Native 方法）引用的对象 | JNI 调用持有的 Java 对象 |
| 方法区中**类静态属性**引用的对象 | `static` 字段 |
| 方法区中**常量**引用的对象 | `static final` 常量 |

可达性分析解决了循环引用问题，但它有一个代价：**扫描整个对象图时必须 STW**，否则用户线程一边改引用、GC 一边标，标记结果就不准。这正是"三色标记"要优化的点。

### 1.3 三色标记：把"全堆 STW 扫描"拆成并发

三色标记把对象分成三种状态：

- **白色**：还没被标记（潜在垃圾）。
- **灰色**：自己标了，但引用的对象还没标完（"正在处理中"）。
- **黑色**：自己和所有引用都标完了（确定存活）。

流程：

1. **初始标记**（STW，极短）：从 GC Roots 直接摸到的对象标灰，只扫根，不扫全堆。
2. **并发标记**（不 STW）：从灰色对象出发遍历对象图，标灰新碰到的、标黑处理完的。这一步最耗时，但和应用线程**并发**跑。
3. **重新标记**（STW，很短）：修正并发期间应用线程改动的引用，把漏标的补上。

> 难点：**并发标记期间应用会改对象图**，可能产生"漏标"（本该黑的对象被挪走引用，变成白）。JVM 用**写屏障（Write Barrier）**在引用赋值那一刻记录变化，重新标记阶段兜底。CMS / G1 的"增量更新"与"原始快照（SATB）"就是两种写屏障策略。

## 二、四种引用：决定"多舍不得放你走"

可达性分析回答"能不能摸到"，引用类型回答"摸到了但有多不想扔"。这四种引用决定了对象在内存吃紧时的命运：

| 引用类型 | 回收时机 | 典型用途 |
|---|---|---|
| **强引用** `Object o = new Object()` | 只要强引用在，绝不回收 | 普通对象，99% 场景 |
| **软引用** `SoftReference` | 内存将溢出前，先回收软引用对象；还不够才抛 OOM | 内存敏感的缓存（如图片缓存） |
| **弱引用** `WeakReference` | 下次 GC 无论内存是否充足都回收 | `ThreadLocal` 的 `Entry`、WeakHashMap |
| **虚引用** `PhantomReference` | 必须配合引用队列，回收时入队，由 `ReferenceHandler` 线程释放堆外内存 | 管理 NIO 的 `DirectByteBuffer` 直接内存 |

**真实示例**：`ThreadLocal` 之所以用弱引用包住 `value`，是为了在业务代码忘记 `remove()` 时，至少 key 能被 GC 掉，减少内存泄漏面（但 value 仍可能被强引用链拖住，所以用完一定要 `remove()`）。

```java
// ThreadLocal 的典型正确用法：用完即清理，避免线程池场景下 value 长期持有
private static final ThreadLocal<SimpleDateFormat> TL = ThreadLocal.withInitial(SimpleDateFormat::new);

void handle() {
    try {
        SimpleDateFormat sdf = TL.get();
        // ... 使用 sdf 做格式化
    } finally {
        TL.remove(); // 关键：线程池线程会被复用，不 remove 会让 value 滞留在线程里
    }
}
```

## 三、三种回收算法：碎片、空间、停顿的三角权衡

标记出垃圾后，怎么把内存收回来？三种基础算法各有取舍。

### 3.1 标记-清除（Mark-Sweep）

先标死活，再把死的清掉，活的原地不动。

- 优点：简单，不需要移动对象。
- 缺点：**内存碎片**。清完一堆空洞，下次分配大对象时连续空间不够，反而触发 Full GC；执行效率不稳定，和对象数量相关。

### 3.2 标记-复制（Copying）

把存活对象整批拷到另一块空白区，原区域整体清空。

- 优点：**无碎片**，分配只需指针碰撞，极快。
- 缺点：**要两倍内存**（或至少一块闲置的"to"区）。

### 3.3 标记-整理（Mark-Compact）

标记后，把存活对象往一端**平移压缩**，腾出连续空间，再把边界外清空。

- 优点：空间连续，**无碎片**，不需要额外内存。
- 缺点：移动存活对象并更新所有引用是重活，必须**全程 STW**。

> 工程映射：新生代对象"死得多、活得少"，适合**复制**（Eden 复制到 Survivor）；老年代对象"活得久"，不适合频繁复制，多用**标记-整理**（或 CMS 的标记-清除 + 碎片问题）。

## 四、分代模型：为什么堆要切成几块

**弱分代假说**：绝大多数对象熬不过第一次 GC。基于这个观察，堆被分为：

- **新生代（Young）**：新对象先来这。由一块 **Eden** + 两块 **Survivor（from / to）** 组成，默认比例 **8 : 1 : 1**（`-XX:SurvivorRatio=8`）。
  - 一次 Minor GC：Eden 和 from 里存活的对象，被**复制**到 to 区；年龄 +1；from / to 角色互换。
  - 年龄到阈值（默认 15，`-XX:MaxTenuringThreshold`）的对象**晋升老年代**。
- **老年代（Old）**：存长生命周期对象。满了就触发 **Major / Full GC**，通常更慢、停顿更长。
- **永久代 / 元空间（Metaspace）**：JDK 8 起方法区实现为**元空间**，放在**本地内存**而非堆里，存类元数据。用 `-XX:MaxMetaspaceSize` 限上限。

**分配担保**：Minor GC 后存活对象若 Survivor 放不下，就由老年代"担保"直接进老年代。所以大对象（如大数组）常通过 `-XX:PretenureSizeThreshold` 直接进老年代，避免 Eden 被瞬间占满。

## 五、常见收集器：吞吐优先 vs 停顿优先

收集器是"算法 + 分代 + 停顿策略"的组合。按目标分两类：

### 5.1 吞吐优先

| 收集器 | 作用代 | 算法 | 特点 | 适用 |
|---|---|---|---|---|
| **Serial / Serial Old** | 新 / 老 | 复制 / 整理 | 单线程，GC 时全应用暂停 | 客户端、极小堆、嵌入式 |
| **Parallel / Parallel Old** | 新 / 老 | 复制 / 整理 | 多线程并行，吞吐最高 | 后台计算、批处理 |

> **版本事实**：**JDK 8 的默认收集器是 Parallel GC（UseParallelGC）**。从 **JDK 9 起 G1 成为默认**（JEP 248），因为对多数服务而言"控停顿"比"榨吞吐"更重要。

### 5.2 停顿优先（低延迟）

| 收集器 | 关键机制 | 停顿 | 代价 | 状态 |
|---|---|---|---|---|
| **CMS** | 并发标记清除 | 初始/重新标记短暂停，清除并发 | 碎片、浮动垃圾、退化 Serial Old | 已废弃（JDK 9 标记废弃，JDK 14 移除） |
| **G1** | 把堆切成 Region，按"回收收益"优先清最有价值的区 | 可预测停顿模型（`-XX:MaxGCPauseMillis`） | 吞吐略低于 Parallel | **JDK 9+ 默认**，服务端主力 |
| **ZGC** | 着色指针 + 读屏障，全程并发 | **亚毫秒级（<1ms）**，与堆大小无关 | 吃 CPU、需更大堆 | **JDK 15 生产可用**（JEP 377），分代 ZGC 于 **JDK 21**（JEP 439，`-XX:+UseZGC -XX:+ZGenerational`） |
| **Shenandoah** | 转发指针 + 读屏障，并发整理 | 亚毫秒级，与堆大小无关 | 每个对象多一个转发指针，吃内存/CPU | **JDK 15 生产可用**（JEP 379），Red Hat 主导 |

> **选型速记**：没有"最好的 GC"，只有"最合适的"。G1 是绝大多数服务的稳妥默认；对延迟极其敏感（如风控、交易网关，要求停顿稳定 <10ms）才上 ZGC / Shenandoah，并准备好更多内存与 CPU。分代 ZGC 在 JDK 21+ 已是多数低延迟场景的更优解。

## 六、真实示例：Spring Boot 服务的 GC 调优骨架

一个常见的后端服务启动参数骨架（JDK 17/21，G1 默认）：

```bash
# 堆大小：生产务必显式设定上下限，避免默认按物理内存比例膨胀
-Xms4g -Xmx4g
# 元空间限上限，防止类加载泄露把本地内存吃满
-XX:MaxMetaspaceSize=256m
# 出现 OOM 时自动 dump 堆，便于事后分析（强烈建议开启）
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/app/heapdump.hprof
# 开启统一 GC 日志（JDK 9+ 的 -Xlog 语法），保留滚动日志
-Xlog:gc*,gc+heap=info,gc+age=trace:file=/var/log/app/gc.log:time,tags,level:filecount=10,filesize=50M
# 若延迟敏感且堆/CPU 充裕，可切 ZGC（JDK 21+ 分代）
# -XX:+UseZGC -XX:+ZGenerational
```

GC 日志里最该盯的三类信号：

- **GC 频次**：Young GC 每秒多次、Full GC 频繁 → 多半是对象晋升太快或堆太小。
- **停顿时长**：G1 的 `-XX:MaxGCPauseMillis` 只是"目标"，不是保证；若长期超标，考虑增大堆或换 ZGC。
- **晋升失败 / 分配担保失败**：老年代跟不上新生代节奏，会触发代价高昂的 Full GC。

## 七、常见追问（面试与排障高频）

**Q1：为什么 GC 一定要 STW？**
标记必须看到"对象图某一刻的稳定快照"，否则并发修改会让标记永远追不平。现代收集器把必须 STW 的环节（初始标记、重新标记）压到极短，把耗时遍历改成并发。

**Q2：为什么会有 Full GC，它为什么慢？**
Full GC 回收整个堆（含老年代），老年代用标记-整理，要移动对象并更新全部引用，必然长时间 STW。常见诱因：老年代碎片/空间不足、元空间不足、`System.gc()` 显式触发、晋升失败。

**Q3：三色标记的"漏标"怎么补？**
靠写屏障记录并发期间的引用变更（CMS 用增量更新，G1 用 SATB 原始快照），在重新标记阶段把这些对象重新标黑。所以重新标记虽 STW，但通常很短。

**Q4：CMS 的"浮动垃圾"是什么？**
并发清除阶段，应用线程仍在产生新垃圾（已死但还没被标），这些要等下一次 GC 才能清，叫浮动垃圾。因此不能等老年代 100% 满才触发 CMS，要留余量。

## 八、踩坑：这些 OOM 你迟早会遇

| 错误 | 含义 | 常见成因 |
|---|---|---|
| `Java heap space` | 堆满 | 对象不释放、缓存无上限、堆太小 |
| `Metaspace` | 元空间满 | 动态生成类过多（CGLIB、Groovy、反射代理） |
| `GC Overhead limit exceeded` | GC 时间 >98% 但回收极少 | 内存泄漏，对象都还"活着" |
| `Direct buffer memory` | 堆外直接内存满 | NIO `DirectByteBuffer` 用太多，未受 `-Xmx` 约束 |
| `Unable to create new native thread` | 线程数到顶 | 线程池失控、系统 `ulimit` 太小 |

**典型坑**：本地内存（元空间、直接内存、线程栈）**不归 `-Xmx` 管**。只调大堆，结果元空间或直接内存把宿主机拖垮——容器里尤其要注意设 `-XX:MaxMetaspaceSize` 和 `-XX:MaxDirectMemorySize`。

**另一个坑**：`System.gc()` 看似"手动清理"，实则触发 Full GC，在延迟敏感服务里是性能地雷。很多框架的"显式释放"最终落到它身上，生产环境常加 `-XX:+DisableExplicitGC` 关掉。

## 九、选择建议：先问业务要什么

- **吞吐优先**（离线计算、批处理、报表）：Parallel GC，给足 CPU 和堆，别纠结停顿。
- **均衡通用**（绝大多数 Web 服务、微服务）：**G1 默认**，调好 `-Xms=-Xmx`、`MaxGCPauseMillis`、开 GC 日志。
- **低延迟敏感**（交易、风控、实时推荐，要求停顿稳定亚十毫秒）：JDK 21+ 上 **分代 ZGC**；堆和 CPU 要预留余量（ZGC 用并发换延迟，吃资源）。
- **大堆且怕碎片**：避开 CMS（已移除）；G1 / ZGC 都会整理，优先 ZGC。

## 十、最佳实践清单

1. **显式设定 `-Xms` 与 `-Xmx` 相等**，避免运行期堆伸缩带来的额外 GC。
2. **永远开 `-XX:+HeapDumpOnOutOfMemoryError`**，出事才有现场。
3. **用 `-Xlog:gc*` 落 GC 日志**，配滚动，排障先看频次和停顿。
4. **容器里设 `MaxMetaspaceSize` / `MaxDirectMemorySize`**，本地内存不归 `-Xmx` 管。
5. **别滥用 `System.gc()`**，延迟敏感服务可 `-XX:+DisableExplicitGC`。
6. **对象尽量短命**：缩小作用域、用完 `close()` / `remove()`，让对象在新生代就死掉，少晋升老年代。
7. **监控优先于调参**：在没看到 GC 日志和堆走势前，不要盲目换收集器或堆大小。

## 总结

GC 的本质是一道题：**顺着 GC Roots 引用链，判定哪些对象还活着，再用合适的算法把它们之外的内存收回来**。可达性分析 + 三色标记解决了"判活且尽量并发"，四种引用解决了"多舍不得放"，三种回收算法在"碎片 / 空间 / 停顿"间权衡，分代模型则利用"对象朝生夕死"的规律把问题拆小。落到选型：JDK 9+ 默认 G1 是稳妥解，吞吐看 Parallel，极致低延迟上 ZGC / Shenandoah——但任何选择都要先有 GC 日志和监控，再谈调优。

记住一句话：**GC 不神秘，它是"标记活的、清掉死的、把活的压紧"的房间打扫；小黑推着清扫车进堆里，沿根引用把活对象留下，把死对象扫走，再把活对象挪到一侧腾出连续空间——停顿，就是它必须让所有人站定那一下的瞬间。**
